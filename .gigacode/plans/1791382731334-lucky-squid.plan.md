# Задача #23: Определить границы доменов и bounded contexts

## Цель
Определить четкие границы между bounded contexts для Otus Payment System, включая aggregates, domain events, интеграционные паттерны и структуру проектов.

---

## 1. Bounded Context Map

### Контексты и их роли

### Типы отношений

| От | Кому | Паттерн | Обоснование |
|---|---|---|---|
| Identity -> Все | Conformist | Все контексты используют только `UserId` |
| Wallets -> Payments | Customer-Supplier | Payments "заказывает" операции баланса у Wallets |
| Payments -> Fraud | ACL | Fraud имеет свою модель рисков; Payments не должен знать internals |
| Все -> Notifications | Publish-Subscribe | Notifications подписывается на события без耦合 |
| Все -> Audit | Publish-Subscribe | Audit подписывается на все события для immutable логирования |

## 2. Detailed Context Analysis

### 2.1 Identity Context

**Ответственность:** User lifecycle, authentication, authorization, JWT/refresh tokens

#### Aggregate Roots

**User** (Aggregate Root)
- **Ответственность:** Регистрация, аутентификация, профиль, статус (Active/Blocked)
- **Инварианты:**
  - Email уникален
  - Password всегда хеширован
  - Status: Active -> Blocked (обратимо только через Admin)
- **Поля:** `Id`, `Email`, `PasswordHash`, `Status`, `CreatedAt`, `UpdatedAt`, `Version`
- **Domain Events:** `UserRegistered`, `UserBlocked`, `UserUnblocked`, `PasswordChanged`

**RefreshToken** (Separate Aggregate Root)
- **Ответственность:** Token rotation, revocation, expiration
- **Инварианты:**
  - Rotation chain: `ReplacedByTokenId` связывает старый с новым
  - При смене пароля все токены отзываются
- **Поля:** `Id`, `UserId`, `Token` (hashed), `ExpiresAt`, `RevokedAt`, `ReplacedByTokenId`

#### Domain Services
- `AuthenticationService` — login, token issuance, refresh, logout
- `PasswordHasherService` — password hashing
- `TokenValidatorService` — JWT validation, revocation check

#### Domain Events (published)

| Event | Routing Key | Payload |
|---|---|---|
| `UserRegistered` | `identity.user.registered` | UserId, Email, Timestamp |
| `UserBlocked` | `identity.user.blocked` | UserId, BlockedBy, Timestamp |
| `UserUnblocked` | `identity.user.unblocked` | UserId, UnblockedBy, Timestamp |
| `PasswordChanged` | `identity.password.changed` | UserId, Timestamp |

### 2.2 Wallets Context

**Ответственность:** Digital wallets, balance operations (top-up, withdrawal), operation history

#### Aggregate Roots

**Wallet** (Aggregate Root)
- **Ответственность:** Lifecycle кошелька, управление балансом, валюта
- **Инварианты:**
  - Баланс не может быть отрицательным
  - Изменения баланса только через явные операции
  - Optimistic locking через `Version`
- **Поля:** `Id`, `UserId`, `Currency`, `Balance`, `Status`, `Version`, `CreatedAt`, `UpdatedAt`
- **Domain Events:** `WalletCreated`, `BalanceDeposited`, `BalanceWithdrawn`, `BalanceTransferredIn`, `BalanceTransferredOut`, `WalletFrozen`, `WalletClosed`

**WalletOperation** (Entity within Wallet aggregate)
- **Ответственность:** Запись каждой операции с audit trail
- **Инварианты:** `BalanceAfter == BalanceBefore +/- Amount`
- **Поля:** `Id`, `WalletId`, `Type`, `Amount`, `Currency`, `BalanceBefore`, `BalanceAfter`, `ReferenceId`, `CreatedAt`

#### Domain Events (published)

| Event | Routing Key |
|---|---|
| `WalletCreated` | `wallet.created` |
| `BalanceDeposited` | `wallet.balance.deposited` |
| `BalanceWithdrawn` | `wallet.balance.withdrawn` |
| `BalanceTransferredIn` | `wallet.balance.transferred.in` |
| `BalanceTransferredOut` | `wallet.balance.transferred.out` |

### 2.3 Payments Context (CORE DOMAIN)

**Ответственность:** Wallet-to-wallet transfers, fees, refunds, merchant payments, payment gateway

#### Aggregate Roots

**Transfer** (Aggregate Root)
- **Ответственность:** End-to-end lifecycle перевода
- **Инварианты:**
  - Source и destination wallets должны существовать
  - Достаточность баланса проверяется перед commit
  - Статус: Pending -> Processing -> Completed OR Failed OR RolledBack
  - Terminal states: Completed, RolledBack, Failed
- **Поля:** `Id`, `SourceWalletId`, `DestinationWalletId`, `Amount`, `Currency`, `FeeAmount`, `FeeWalletId`, `Status`, `FraudCheckStatus`, `ErrorMessage`, `CreatedAt`, `CompletedAt`, `UpdatedAt`
- **Domain Events:** `TransferCreated`, `TransferProcessing`, `TransferCompleted`, `TransferFailed`, `TransferRolledBack`, `TransferBlockedByFraud`

**Payment** (Aggregate Root) — Phase 6
- **Ответственность:** Merchant-initiated payments, payment links, refunds
- **Поля:** `Id`, `MerchantId`, `TransferId`, `Amount`, `Currency`, `Status`, `PaymentLink`, `ExpiresAt`, `WebhookUrl`
- **Domain Events:** `PaymentCreated`, `PaymentPaid`, `PaymentRefunded`, `PaymentExpired`

**Merchant** (Aggregate Root) — Phase 6
- **Ответственность:** Merchant registration, API key management, webhooks
- **Domain Events:** `MerchantCreated`, `MerchantSuspended`, `ApiKeyGenerated`

#### Domain Services
- `TransferService` — orchestrates full transfer lifecycle (validate -> debit -> credit -> complete)
- `FeeCalculationService` — calculates fees based on amount, currency, tier
- `RefundService` — handles partial and full refunds
- `PaymentGatewayService` — merchant-facing API

#### Domain Events (published)

| Event | Routing Key |
|---|---|
| `TransferCreated` | `payment.transfer.created` |
| `TransferProcessing` | `payment.transfer.processing` |
| `TransferCompleted` | `payment.transfer.completed` |
| `TransferFailed` | `payment.transfer.failed` |
| `TransferRolledBack` | `payment.transfer.rolledback` |
| `TransferBlockedByFraud` | `payment.transfer.blocked` |
| `PaymentCreated` | `payment.payment.created` |
| `PaymentPaid` | `payment.payment.paid` |
| `PaymentRefunded` | `payment.payment.refunded` |

### 2.4 Fraud Context

**Ответственность:** Fraud detection, risk scoring, blacklists, operational limits

#### Aggregate Roots

**FraudRule** (Aggregate Root)
- **Ответственность:** Rules для fraud detection (thresholds, frequency, blacklists)
- **Поля:** `Id`, `Name`, `Type`, `Parameters` (JSON), `Severity`, `Action`, `IsActive`
- **Types:** `MaxSingleAmount`, `MaxDailyAmount`, `MaxFrequency`, `Blacklist`, `RiskScore`

**FraudAlert** (Aggregate Root)
- **Ответственность:** Records fraud alerts from rule evaluation
- **Поля:** `Id`, `TransferId`, `UserId`, `RuleId`, `Severity`, `Status`, `Details`, `CreatedAt`, `ResolvedAt`

#### Domain Services
- `FraudEvaluationService` — evaluates transfer against all active rules
- `RiskScoreCalculatorService` — rolling risk score based on recent history

#### Domain Events (published)

| Event | Routing Key |
|---|---|
| `FraudAlertRaised` | `fraud.alert.raised` |
| `FraudAlertResolved` | `fraud.alert.resolved` |
| `TransferBlockedByFraud` | `fraud.transfer.blocked` |

## 3. Cross-Context Communication

### 3.1 Synchronous (REST API)

| Caller | Callee | Purpose | Method |
|---|---|---|---|
| Payments | Wallets | Debit source wallet | `POST /wallets/{id}/debit` |
| Payments | Wallets | Credit destination | `POST /wallets/{id}/credit` |
| Payments | Fraud | Evaluate risk | `POST /fraud/evaluate` |
| Payments | Identity | Validate user | `GET /users/{id}` |

**Pattern:** Payments orchestrates. Sync calls to Wallets (debit/credit) within saga pattern. If credit fails, Payments initiates compensating transaction (rollback).

### 3.2 Asynchronous (RabbitMQ Events)

#### Exchange Strategy
```
otus.{context}.{entity}.{action}
```
Examples: `otus.identity.user.registered`, `otus.payments.transfer.completed`

#### Event Publishing Matrix

| Publisher | Events | Exchange |
|---|---|---|
| Identity | UserRegistered, UserBlocked, PasswordChanged | `otus.identity` |
| Wallets | WalletCreated, BalanceDeposited, BalanceWithdrawn, BalanceTransferredIn, BalanceTransferredOut | `otus.wallets` |
| Payments | TransferCreated, TransferProcessing, TransferCompleted, TransferFailed, TransferRolledBack, TransferBlockedByFraud, PaymentCreated, PaymentPaid, PaymentRefunded | `otus.payments` |
| Fraud | FraudAlertRaised, FraudAlertResolved, TransferBlockedByFraud | `otus.fraud` |

#### Event Subscriptions

| Consumer | Subscribes To | Purpose |
|---|---|---|
| Notifications | All exchanges | User-facing notifications |
| Audit | All exchanges | Immutable audit logging |
| Fraud | `payment.transfer.created`, `wallet.balance.*` | Async risk scoring |

### 3.3 Event Schema Convention

```json
{
  "eventId": "guid",
  "eventType": "fully.qualified.event.name",
  "timestamp": "ISO 8601 UTC",
  "correlationId": "guid",
  "causationId": "guid?",
  "context": "Identity|Wallets|Payments|Fraud",
  "data": { /* Event-specific payload */ }
}
```

**Naming:**
- Event class: `PascalCase` (e.g., `TransferCompleted`)
- Routing key: `snake_case` with context prefix (e.g., `payment.transfer.completed`)
- JSON properties: `camelCase`

## 4. Anti-Corruption Layers

### 4.1 Payments ACL for Identity
**Problem:** Payments must validate `UserId` exists but must not depend on Identity's User entity, roles, or password logic.

**Solution:** Payments defines minimal `ExternalUser` DTO (`Id`, `Email`). Calls `GET /users/{userId}`. Never imports Identity's domain model.

### 4.2 Payments ACL for Wallets
**Problem:** Payments orchestrates transfers but must not depend on Wallets' internal balance calculation.

**Solution:** Payments defines `WalletBalance` DTO. Calls Wallets' debit/credit APIs. Wallets owns balance logic entirely.

### 4.3 Fraud ACL for Payments
**Problem:** Fraud has its own risk model that Payments must not understand.

**Solution:** Payments calls Fraud's evaluation API with minimal request DTO. Fraud returns `Pass`/`Block` with reason code.

## 6. Key Design Decisions

### Почему Payments — Core Domain?
- Здесь создается основная бизнес-ценность (переводы денег)
- Payments orchestrates the entire money movement flow
- Wallets, Fraud, Notifications — supporting subdomains

### Почему Wallets — upstream для Payments?
- Payments "заказывает" операции баланса у Wallets
- Wallets определяет контракт debit/credit
- Payments не знает internals Wallets (только через API)

### Почему Fraud — sync + async?
- **Sync:** Blocking fraud check during transfer validation (необходимо для принятия решения "allow/deny" в реальном времени)
- **Async:** Alert generation, risk scoring updates (не блокирует основной flow)

### Почему Audit — отдельный контекст?
- Audit — compliance concern, не user communication
- Notifications — user-facing, может retry, имеет templates
- Audit — immutable, append-only, regulatory requirement
- Разделение ответственности: Audit не удаляет/не модифицирует данные

### Почему все контексты используют только UserId?
- Identity — единственный источник правды о пользователях
- Избегание дублирования user data
- Consistency через ACL pattern
