# Требования к аутентификации и авторизации

## 1. Цель

Определить базовые требования к аутентификации и авторизации в **Otus Payment System** для защиты учетных записей пользователей, кошельков, платежей и административных операций.

## 2. Область действия

Документ покрывает:

- Аутентификацию пользователей (регистрация, вход, жизненный цикл токенов)
- Авторизацию API (на основе ролей и политик)
- Меры безопасности для операций, связанных с identity
- Требования к аудиту и наблюдаемости

Вне scope (для этого issue):

- Интеграция с внешними IdP (Google, Azure AD и т.д.)
- Детали реализации MFA
- Модель API-ключей мерчантов (будет в фазе payment gateway)

## 3. Термины

- **Аутентификация**: подтверждение личности пользователя.
- **Авторизация**: проверка, может ли аутентифицированный пользователь выполнить действие.
- **Access Token**: короткоживущий JWT для доступа к API.
- **Refresh Token**: долгоживущий токен для получения нового access token.
- **RBAC**: role-based access control.

## 4. Акторы и роли

Минимальные роли:

- `User` — стандартные операции учетной записи.
- `Admin` — операционные/административные endpoint’ы.
- `Support` (опционально на первом этапе) — read-only операционный доступ.

Расширение набора ролей в будущем должно поддерживаться без поломки существующих токенов.

## 5. Функциональные требования — Аутентификация

### 5.1 Регистрация

1. Система должна позволять регистрацию пользователя с уникальным email.
2. Система должна хранить пароль как стойкий односторонний хэш (никогда не plaintext).
3. Система должна валидировать парольную политику (минимальная длина и сложность).
4. Система должна возвращать понятные ошибки валидации без раскрытия внутренних деталей.

### 5.2 Вход

1. Система должна аутентифицировать по email + password.
2. При успешном входе система должна выдавать:
   - JWT access token
   - Refresh token
3. При неуспехе система должна возвращать общий auth error (`invalid credentials`).

### 5.3 Жизненный цикл токенов

1. Access token должен быть короткоживущим (например, 15 минут).
2. Refresh token должен поддерживать отзыв и ротацию.
3. Система должна предоставлять endpoint обновления токена.
4. Система должна поддерживать logout через отзыв refresh token.
5. Система должна инвалидировать refresh token после смены пароля.

### 5.4 Управление паролем

1. Система должна поддерживать смену пароля для аутентифицированных пользователей.
2. Система должна поддержать flow сброса пароля (через email) на следующей итерации.
3. История/запрет повторного использования паролей — опционально для первого релиза.

## 6. Функциональные требования — Авторизация

### 6.1 Контроль доступа к API

1. Все защищенные endpoint’ы должны требовать валидный JWT bearer token.
2. Авторизация должна быть policy-based с role checks там, где это применимо.
3. Анонимный доступ должен быть явно разрешен только для:
   - registration
   - login
   - health/public endpoint’ов (при необходимости)

### 6.2 Владение ресурсами

1. Пользователь должен иметь доступ только к своим кошелькам, переводам и данным профиля.
2. Роль Admin может иметь доступ к межпользовательским операционным endpoint’ам.
3. Проверки владения должны применяться в application/domain layer, а не только в controller layer.

### 6.3 Минимальная матрица политик endpoint’ов

- `POST /auth/register` — anonymous
- `POST /auth/login` — anonymous
- `POST /auth/refresh` — anonymous (требуется валидный refresh token)
- `POST /auth/logout` — authenticated user
- Endpoint’ы кошельков/платежей — authenticated user + ownership policy
- Admin endpoint’ы — роль `Admin`

## 7. Требования безопасности

1. Ключ подписи JWT должен храниться безопасно (без hardcode, использовать configuration secrets).
2. Использовать HTTPS во всех non-local окружениях.
3. Реализовать защиту от brute-force для login (rate limiting / lockout strategy).
4. Не раскрывать чувствительные детали в ошибках аутентификации.
5. Включать claims `sub`, `email`, `role`, `jti`, `exp` в access token.
6. Валидировать issuer/audience/signature/lifetime для каждого токена.
7. Refresh token’ы должны храниться server-side с признаком отзыва.
8. Security events должны быть аудируемыми (успешный/неуспешный login, refresh, logout, смена ролей).

## 8. Нефункциональные требования

1. Endpoint’ы аутентификации должны быть наблюдаемыми (logs + metrics).
2. Ошибки авторизации (`403`) и аутентификации (`401`) должны различаться.
3. Подсистема auth должна быть stateless для валидации access token.
4. Валидация токена должна давать минимальный overhead в обработке запроса.

## 9. Требования к данным и хранению

1. Данные identity должны включать:
   - User ID
   - Email
   - PasswordHash
   - Roles
   - Status (Active/Blocked)
   - CreatedAt/UpdatedAt
2. Данные refresh token должны включать:
   - Token ID / hash
   - User ID
   - ExpiresAt
   - RevokedAt
   - ReplacedByTokenId (для цепочек ротации)

## 10. Требования к аудиту и compliance

1. Система должна логировать:
   - попытки регистрации
   - успешный/неуспешный login
   - refresh/revocation токенов
   - изменения назначения ролей
2. Логи не должны хранить секреты/пароли/токены в plaintext.
3. Для auth-запросов должен присутствовать Correlation ID.

## 11. Критерии приемки (Issue #15)

Issue считается завершенным, когда:

1. Создан и согласован `docs/auth-requirements.md`.
2. Задокументированы обязательные роли и модель доступа.
3. Задокументированы требования к JWT и жизненному циклу refresh token.
4. Задокументированы минимальные требования по безопасности и аудиту.
5. Зафиксирована граница между in-scope и out-of-scope.

## 12. Примечания к реализации (для следующих issue)

Рекомендуемые следующие задачи:

1. Реализовать модель сущностей ASP.NET Core Identity (или эквивалент).
2. Добавить настройку JWT bearer authentication.
3. Ввести policy-based authorization handlers для ownership checks.
4. Реализовать хранение refresh token + ротацию + отзыв.
5. Добавить integration tests для `401/403`, role checks и ownership checks.
