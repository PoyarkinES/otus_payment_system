## Что сработало

- **Интеграционные тесты на реальном PostgreSQL.** Проверяются не только правила домена, но и транзакционные сценарии, ledger и конкуренция.
- **Bootstrap вместо второй БД/volume.** Идемпотентное создание `otus_wallets` позволило добавить Wallets на существующий PostgreSQL, не удаляя данные Identity.
- **Проверка через публичный Gateway.** Smoke подтвердил авторизацию и маршрут до Wallets в собранном Compose-стеке.
- **Закреплённые SHA-образы.** Compose использует конкретные образы; после обновления Shared можно повторить smoke на воспроизводимом наборе сервисов.
- **Общий пакет как место исправления.** Выравнивание IdentityModel в Shared устранило рассинхронизацию, затрагивавшую Gateway, Identity и Wallets, а не только один хост.

## Что кусало

| Проблема | Цена | Вывод |
|---|---|---|
| В опубликованных сервисах смешались версии IdentityModel: `Tokens` `8.14.0`, остальные компоненты — `8.0.1`; Gateway не мог декодировать JWT | Авторизованные запросы возвращали `401`, хотя регистрация и login проходили | Выравнивать всё семейство пакетов в Shared и проверять итоговый `.deps.json` каждого хоста |
| CI не видел собранный Shared `1.0.1` до публикации в NuGet feed (`NU1102`) | PR-проверки restore останавливались до сборки потребителей | Передавать пакетные артефакты как локальный NuGet feed в CI и Docker build |
| Новый сервис зависел от наличия отдельной БД, а старый volume Identity нужно было сохранить | Нельзя было полагаться только на init SQL чистого volume | Использовать идемпотентный bootstrap и проверять оба случая без `down -v` |
| Генерируемый строгий BFF-контракт потребовал обновить тестовые фикстуры клиента | Client typecheck падал на устаревших mock-ответах | При изменении OpenAPI обновлять фикстуры вместе с контрактом и запускать typecheck |

## Правила, которые забираем в M3

1. Версии взаимосвязанных библиотек IdentityModel выравниваются централизованно; runtime-граф проверяется у всех потребителей.
2. CI должен проверять изменения пакета из артефакта текущего PR, а публикация в feed остаётся отдельным релизным шагом.
3. Compose smoke запускать в изолированном project name; для сохранения тестовых данных использовать `down` без `-v`.
4. Проверять весь путь через Gateway после публикации образов, а не считать зелёные unit-тесты доказательством интеграции.
5. Закрывать задачи после готовности реализации, CI, smoke и документации; прикладывать к issue конкретный результат проверки.
