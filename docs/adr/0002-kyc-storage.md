# ADR 0002. KYC-документы: MongoDB для метаданных + MinIO для файлов

- **Статус:** Proposed
- **Дата:** 2026-10-30
- **Контекст:** post-1.0, M7 «KYC/Onboarding»
- **Связанные задачи:** #73 (эпик M7), #74–#78

## Контекст

Для подтверждения личности нужны:

- разные типы документов (паспорт РФ, загранпаспорт, водительское удостоверение);
- разные ответы провайдера верификации;
- сканы/фото документов;
- история проверок и статусов;
- строгий контроль доступа и аудит.

Это чувствительные персональные данные. Ошибка в хранении — это не «баг в учебном проекте», а утечка PII.

## Решение

1. Ввести отдельный bounded context **KYC/Onboarding** (`Kyc/`), не складывать это в Identity или Payments.
2. **Метаданные KYC-кейса** хранить в **MongoDB**, коллекция `kyc_cases`:
   - `userId`, `status`, `documents[]`, `providerResult`, `createdAt`, `updatedAt`;
   - документы разных типов и ответы провайдера — вложенные документы с разной схемой;
   - индексы: `userId`, `status`, `createdAt`; TTL/retention — отдельной политикой.
3. **Файлы** хранить в **MinIO** (S3-совместимое объектное хранилище), private bucket `kyc-documents`:
   - в Mongo — только `fileId`, content-type, размер, хэш, ссылка;
   - доступ к файлу — только через KYC-сервис, короткоживущий signed URL;
   - server-side encryption, версии/retention.
4. **Не использовать GridFS** для сканов: это раздувает БД, усложняет бэкапы, не даёт нормальные lifecycle/signed URL.
5. **PII-минимизация:**
   - номера документов — хеш + маска (последние 4 символа), не plaintext;
   - сырые сканы — только в MinIO, не в логах;
   - в логах — `kycCaseId`, `userId`, `documentType`, `status`, без номеров и файлов;
   - в dev/demo — **только синтетические документы**.
6. **Доступ:** только KYC-сервис имеет доступ к Mongo/MinIO. Gateway не читает Mongo и не отдаёт файлы напрямую. Admin-доступ — отдельная роль + аудит.
7. **Аудит:** каждое создание/просмотр/изменение статуса/выдача signed URL — событие аудита (кто, когда, какой кейс, действие).

## Почему Mongo, а не PostgreSQL JSONB

| Критерий | MongoDB | PostgreSQL JSONB |
|---|---|---|
| Разные типы документов и ответов провайдера | Гибкая документная модель | JSONB тоже может, но схема и запросы менее удобны |
| Вложенные массивы документов | Естественно | JSONB-массив, сложнее индексировать |
| Транзакции между сервисами | Не нужны: KYC не двигает деньги | Сильные транзакции, но KYC не транзакционный контур |
| Полиглот-персистентность | Явный отдельный контекст | Один Postgres на всё |

KYC не участвует в денежных транзакциях, поэтому строгая реляционная целостность здесь не критична. Если бы KYC влиял на баланс/лимиты в той же транзакции — выбрали бы PostgreSQL.

## Почему MinIO, а не Mongo/GridFS/локальный диск

- S3-совместимый API, локально в Docker, в production — тот же код на AWS S3/MinIO.
- Нормальные политики доступа, версии, encryption, lifecycle, signed URL.
- Файлы не конкурируют с метаданными за ресурсы БД.
- Локальный диск не переживёт контейнер и не даст воспроизводимость.

## Последствия

**Плюсы**

- Гибкая схема KYC-кейса для разных документов и провайдеров.
- Файлы отделены от метаданных; проще бэкап/retention/security.
- Полиглот-персистентность обоснована доменом, а не «хочу Mongo».
- gRPC-контракт может отдавать только статус, не раскрывая документы.

**Минусы / риски**

- Два новых компонента (Mongo, MinIO) и их эксплуатация.
- Нужны шифрование, ротация ключей, аудит, retention.
- Mongo не даёт «бесплатной» согласованности с Payments; статус KYC передаётся через API/события.
- Соблазн хранить PII в Mongo «как есть» — запрещён.

**Меры**

- Только синтетические данные в репозитории и демо.
- Threat model в W25, security checklist в W28.
- Feature flag в Payments: KYC не блокирует 1.0.
- Явные границы: KYC не заменяет Identity и не управляет токенами.

## Что этот ADR не решает

- Реальный провайдер верификации, OCR, liveness.
- Юридическое соответствие 152-ФЗ/GDPR/PCI DSS.
- Шифрование на уровне полей Mongo (CSFLE) — можно добавить позже.
- Admin UI.
